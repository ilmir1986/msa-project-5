#### Обоснование выбора технологий

**Почему Spring Batch:**

1. **Chunk-oriented processing**: Оптимальная модель для построчной обработки больших CSV-файлов. Позволяет контролировать размер транзакции (chunk size = 100–1000), снижая нагрузку на БД.

2. **Встроенная отказоустойчивость**:
    - `retry()` — автоматические повторные попытки при временных сбоях (таймауты БД, сетевые ошибки)
    - `skip()` — пропуск невалидных записей без остановки всего job
    - `no-rollback-for()` — контроль над транзакционным поведением

3. **Restartability**: Состояние job сохраняется в таблицах `BATCH_JOB_EXECUTION`, `BATCH_STEP_EXECUTION`. При сбое можно перезапустить обработку с места остановки, а не с начала.

4. **Интеграция с экосистемой**:
    - Полная совместимость с Spring Boot 3.x, Spring Data JPA, Spring Cloud
    - Легкая настройка через Java Config, поддержка YAML-конфигураций
    - Интеграция с Actuator для мониторинга

5. **Масштабируемость**:
    - Поддержка `partitioning` для параллельной обработки разных сегментов данных
    - Возможность выноса job в отдельные worker-ноды в Kubernetes

6. **Наблюдаемость**:
    - Встроенные метрики: `spring.batch.job.duration`, `spring.batch.item.read.count`
    - Легкая интеграция с Prometheus + Grafana через Micrometer

**Архитектурные решения:**

- **Chunk size = 100**: Баланс между производительностью и потреблением памяти. При необходимости можно увеличить до 500–1000 для более быстрой обработки.
- **UPSERT через ON CONFLICT**: Гарантирует идемпотентность повторных запусков, избегает дубликатов.
- **JDBC-lookup в процессоре**: Прямой запрос к loyality_data без кэширования — достаточно для текущего объёма данных. При росте можно добавить Caffeine/Redis.
- **Отделение Reader/Processor/Writer**: Соблюдение SRP, упрощение тестирования и будущей декомпозиции на микросервисы.

### <a name="_bjrr7veeh80c"></a>**Альтернативы**

#### 1. Spring Integration
**Плюсы**: Гибкий routing, трансформация, поддержка множества протоколов.  
**Минусы**:
- Более высокий порог входа, сложная конфигурация
- Избыточен для линейного ETL-пайплайна
- Меньше встроенной поддержки batch-паттернов (chunk, restart)

#### 2. Apache Camel
**Плюсы**: Богатая библиотека компонентов, мощные EIP-паттерны.  
**Минусы**:
- Значительный overhead для простой задачи "читать → обогатить → записать"
- Сложнее отладка и мониторинг
- Меньшая интеграция с Spring Boot Actuator

#### 3. Кастомное решение на CompletableFuture + JDBC
**Плюсы**: Полный контроль, минимальные зависимости.  
**Минусы**:
- Придётся самостоятельно реализовывать retry, skip, transaction management, restart
- Высокие трудозатраты, риск ошибок
- Сложнее поддержка и онбординг новых разработчиков

#### 4. Apache Spark
**Плюсы**: Отличная производительность на больших данных, распределённая обработка.  
**Минусы**:
- Избыточен для 400K строк/день (это ~5 записей/сек в пике)
- Требует отдельного кластера, сложного деплоя
- Не интегрируется нативно с транзакциями PostgreSQL

#### 5. Cloud-native сервисы (AWS Glue, Azure Data Factory, GCP Dataflow)
**Плюсы**: Managed-сервисы, автоскейлинг, встроенный мониторинг.  
**Минусы**:
- Vendor lock-in, сложнее миграция между облаками
- Дороже при росте нагрузки
- Меньше контроля над логикой обработки

**Вывод по альтернативам**:  
Spring Batch предоставляет оптимальный баланс между функциональностью, простотой интеграции и поддерживаемостью для текущего масштаба TradeWare. При росте нагрузки в 10–100× можно рассмотреть гибридный подход: Spring Batch для оперативных задач + Spark для аналитических пайплайнов.

### Недостатки, ограничения, риски

|                **Риск**                | **Вероятность** | **Влияние** | **Митигация**                                                                                   |
|:--------------------------------------:|:----------------|:------------|:------------------------------------------------------------------------------------------------|
|   Блокировки БД при массовой записи    | Средняя         | Высокое     | Использовать batch-вставку, оптимизировать индексы, настроить isolation level                   |
|     Память при большом chunk size      | Низкая          | Среднее     | Начать с chunk=100, мониторить heap, добавить tuning при необходимости                          |
|   Отсутствие кэша для loyality_data    | Средняя         | Низкое      | При росте нагрузки добавить Caffeine с TTL=5 мин                                                |
| Сложность отладки распределённых сбоев | Средняя         | Среднее     | Внедрить structured logging (JSON), correlation ID, интеграцию с ELK                            |
|          Миграция с монолита           | Высокая         | Высокое     | Реализовать ETL как отдельный модуль с чётким контрактом, чтобы в будущем вынести в микросервис |
|   Зависимость от Spring Batch версий   | Низкая          | Низкое      | Следовать LTS-версиям Spring, тестировать обновление в staging                                  |
