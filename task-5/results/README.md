# Выбранные метрики для Spring Batch ETL

---

## Принципы выбора метрик

При проектировании метрик я руководствовался подходом **RED + USE**:

| Принцип                      | Применение в контексте Batch ETL                          |
|------------------------------|-----------------------------------------------------------|
| **Rate** (частота)           | Сколько записей обрабатывается в единицу времени          |
| **Errors** (ошибки)          | Доля неудачных запусков / обработанных записей с ошибками |
| **Duration** (длительность)  | Время выполнения шагов и всего job                        |
| **Utilization** (утилизация) | Загрузка JDBC pool, памяти, CPU во время выполнения batch |

## Выбранные метрики

| Метрика                                 | Тип       | Пример значения | Описание                                                                         |
|-----------------------------------------|-----------|-----------------|----------------------------------------------------------------------------------|
| **`spring_batch_processed_total`**      | `Gauge`   | `42`            | Количество записей (продуктов), обработанных за выполнение batch job.            |
| **`spring_batch_job_duration_seconds`** | `Gauge`   | `15`            | Длительность выполнения job в секундах. Помогает понять производительность.      |
| **`spring_batch_job_success_total`**    | `Counter` | `1`             | Количество успешных запусков job (увеличивается при каждом успешном выполнении). |
| **`spring_batch_job_failure_total`**    | `Counter` | `0`             | Количество неуспешных запусков job. Полезно для мониторинга ошибок.              |

## Детальное описание

### `spring_batch_processed_total` (Gauge)
```yaml
purpose: "Оценка прогресса и пропускной способности"
why_gauge: "Значение сбрасывается после каждого запуска job — актуальный счётчик в рамках одного execution"
alert_threshold: "< 100 записей/мин при ожидаемых 500 → предупреждение о деградации"
dashboard_use: "График 'Processed items over time' с аннотацией начала/конца job"
```

**Почему не Counter?**  
В контексте одного запуска job нам важно видеть *текущий прогресс*, а не кумулятивное значение за всё время жизни приложения. После завершения job значение сбрасывается — это поведение Gauge.

---

### `spring_batch_job_duration_seconds` (Gauge)
```yaml
purpose: "Контроль SLA и выявление аномалий выполнения"
why_gauge: "Фиксирует длительность последнего выполнения; для исторического анализа Prometheus сохраняет временной ряд"
alert_threshold: "> 300 сек → критическое предупреждение (деградация производительности)"
dashboard_use: "Тренд длительности за последние 24ч + сравнение с baseline"
```

**Почему не Histogram?**  
Histogram полезен для анализа распределения, но для batch-задач, запускаемых по расписанию, ключевой вопрос: *«Уложился ли последний запуск в ожидаемое окно?»*. Для глубокого анализа распределения можно добавить `spring_batch_job_duration_seconds_bucket` в будущем.

---

### `spring_batch_job_success_total` / `failure_total` (Counter)
```yaml
purpose: "Мониторинг стабильности и расчёт availability"
why_counter: "Кумулятивный счётчик — идеально для агрегации за период (сутки/неделя) и расчёта ошибок"
alert_threshold: "increase(failure_total[1h]) > 0 → немедленное оповещение"
dashboard_use: "Статус-панель 'Last 10 executions' + график накопления ошибок"
```

**Расчёт Availability**:
```promql
# Доля успешных запусков за последние 24 часа
sum(increase(spring_batch_job_success_total[24h])) 
/ 
(sum(increase(spring_batch_job_success_total[24h])) + sum(increase(spring_batch_job_failure_total[24h])))
```

## Обоснование архитектурных решений

### Отправка метрик: PushGateway
**Выбрано:** Micrometer PushGateway (не Prometheus Agent / JMX Exporter)

**Причины:**
1. **Эпизодический характер job**: приложение запускается, выполняет пакетную обработку и завершается. Pull-модель Prometheus не успеет заскрапить метрики до остановки контейнера.
2. **Гарантия доставки**: метрики пушатся в конце выполнения, фиксируя финальное состояние независимо от времени жизни контейнера.
3. **Простота**: не требуется настройка service discovery или постоянных network rules для scrape.

**Компромиссы:**
- Метрики "залипают" в PushGateway до перезапуска → решается очисткой по `job`-label при каждом запуске
- Не подходит для high-cardinality labels → в проекте используются только `job`, `instance`, `step`

### Логирование: ELK + Filebeat
**Выбрано:** JSON-логи в stdout → Filebeat (container input) → Logstash → Elasticsearch → Kibana

**Причины:**
1. **12-factor app**: логирование в stdout позволяет Docker управлять ротацией и сбором без изменения кода приложения
2. **Централизация**: Filebeat с `add_docker_metadata` автоматически обогащает логи метаданными контейнера (имя, образ, labels)
3. **Гибкость парсинга**: Logstash позволяет нормализовать поля (`msg`→`message`, `logger`→`logger_name`) без пересборки приложения
4. **Корреляция с трейсингом**: структура JSON-логов совместима с добавлением `traceId`/`spanId` в будущем

### Оповещения: Prometheus Alerting Rules
**Выбрано:** YAML-правила в Prometheus (не Grafana Alerting)

**Причины:**
1. **Version control**: правила хранятся в репозитории, проходят review и CI/CD
2. **Прозрачность**: логика алертов видна в коде, не зависит от UI-состояния Grafana
3. **Портативность**: правила работают независимо от Grafana, могут использоваться с любым Alertmanager
4. **Достаточно для задания**: 2 метрики покрывают основные сценарии (сбой + деградация)

**Почему не Alertmanager с уведомлениями?**
- Для MVP достаточно визуального контроля в Prometheus UI / Grafana
- Интеграция с email/Slack требует внешних endpoint'ов, что выходит за рамки учебного задания
- При необходимости: добавить Alertmanager и `webhook_configs` — 3 строки в конфиге
